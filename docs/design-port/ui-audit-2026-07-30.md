## P0 — PDP images are not clickable and have no lightbox

File: `apps/web/src/components/listings/property-gallery.tsx`

This is the headline defect. The PDP gallery mosaic looks interactive and is not.

1. **The hero tile is not a control.** L38 is a `<figure>` carrying `cursor-pointer`, with **no `onClick`, no `href`, and no dialog**. The pointer cursor advertises an interaction that does not exist:

   ```
   group relative col-span-1 m-0 aspect-[16/10] cursor-pointer overflow-hidden
   md:row-span-2 md:aspect-auto md:h-full md:min-h-0
   ```

2. **Thumbnails only shuffle, they don't open anything.** L65–71 are real `<button>`s, but the sole action is `onClick={() => setHeroIdx(i)}` (L69) — swap the image into the hero slot. There is no viewer on the page.

3. **The "All N photos" badge is not a button.** L82–86 render it as a decorative `<span>` **nested inside the last thumbnail `<button>`**. Clicking it swaps the hero image rather than opening a gallery. Because it is a `span` inside a `button`, it can never become its own control without being lifted out of that element.

4. **Most photos are unreachable.** L26–29 does `.slice(0, 4)`, so only 5 images are ever rendered. On a 30-photo listing, **25 photos exist in the data and are reachable from nowhere on the site.**

5. **Mobile sees one photo and no photo count.** L71 marks the thumbnails `hidden … md:block`. The count badge lives inside a hidden tile, so on a phone the user sees a single image with no indication that more exist.

### There is already a working pattern to reuse

`apps/web/src/components/communities/gallery-photos-dialog.tsx` implements a full-screen viewer: `Dialog` from `@mvp-realty/ui/components/ui/dialog`, `h-dvh max-h-dvh w-screen`, a scrollable `grid-cols-1 sm:grid-cols-2 lg:grid-cols-3` over **every** image, and a custom close button. It is wired into `communities/gallery.tsx:40` only.

It is a **grid modal, not a per-image lightbox** — no prev/next, no start index.

### Does the lightbox have arrows for navigating photos? No

To be explicit, since it is easy to assume otherwise: **there are no navigation arrows anywhere in the photo-viewing experience, because on the PDP there is no viewer at all.** The two things that exist:

- `communities/gallery-photos-dialog.tsx` — a scrollable **grid of thumbnails**. No prev/next controls, no concept of a "current" photo, no start index. You scroll a wall of images.
- The PDP thumbnails — swap the hero in place (`property-gallery.tsx:69`). Not navigation, and there is no forward/back affordance.

Note that `packages/ui/src/components/ui/carousel.tsx` already exists (Embla-based, with prev/next), and Swiper is already a dependency (`listings/listing-slider.tsx`). Arrow navigation does not require a new library — it requires building the viewer.

### Recommended fix

- Generalize `GalleryPhotosDialog` to accept a `startIndex` and **prev/next arrow navigation**, and to take `GalleryShot[] | CmsImage[]`. Update the existing caller (`communities/gallery.tsx:40`) alongside. Arrows should be paired with keyboard `←`/`→` handling, swipe on touch, and a "n of N" counter — arrows alone give no sense of position.
- In `property-gallery.tsx`: make the hero a real trigger, lift the "All N photos" badge out of the thumbnail button into its own control, and add a **mobile-visible** trigger so phone users can reach the full set.
- Confirm the full array reaches the view (`apps/web/src/data/property.ts:196`, `gallery: detail.gallery`).
- No new dependency needed — `packages/ui/src/components/ui/dialog.tsx` and `carousel.tsx` already exist.

## P0 — the mobile filter sheet is cut off behind the sticky nav

Reported from a real device (Android Chrome, ~390px wide). Confirmed root cause: **the sticky site nav has a higher `z-index` than the sheet.**

| Element | File | z-index |
| --- | --- | --- |
| Site nav (`sticky top-0`) | `apps/web/src/components/site-nav-interactive.tsx:27` | `z-60` |
| Sheet overlay (`fixed inset-0`) | `packages/ui/src/components/ui/sheet.tsx:33` | `z-50` |
| Sheet content (`fixed inset-y-0 left-0`) | `packages/ui/src/components/ui/sheet.tsx:57` | `z-50` |

The filter sheet is `side="left"` with `inset-y-0 h-full` (`listings-browser.tsx:152–155`), so it *is* full height — but the nav paints on top of its first ~80px. Symptoms visible in the report, all explained by this one cause:

- The nav bar renders **bright and undimmed** while the rest of the page behind the sheet is correctly dimmed by `bg-black/50` — the overlay is painting *under* the nav.
- The top of the filter panel is sliced off. The dark `bg-primary` panel header ("Refine") is reduced to a clipped strip at the top of the sheet.
- The sheet cannot be dismissed by tapping the top region, because those taps land on the nav, not the overlay.

Because `SheetContent` has `overflow-hidden p-0` (`listings-browser.tsx:154`) and the scroll container is a sibling below (L159), the hidden header does not scroll into view — it is unreachable, not merely scrolled away.

### This is not limited to the filter sheet

`packages/ui/src/components/ui/dialog.tsx:34,56` uses the same `z-50` for overlay and content. So **every dialog in the app renders beneath the nav**, including `communities/gallery-photos-dialog.tsx` — and the PDP lightbox recommended in the P0 above will inherit the same bug unless this is fixed first.

**Fix:** establish one z-index scale and put overlays above the chrome. Either lower the nav below `z-50`, or raise `SheetOverlay`/`SheetContent`/`DialogOverlay`/`DialogContent` above the nav (e.g. `z-70`). Fixing it in `packages/ui` corrects the sheet, both galleries, and the future lightbox at once. Related: the ad-hoc `z-40` / `z-50` / `z-60` values on `quick-filter-bar.tsx:40`, `section-tabs.tsx:52`, and the nav are currently unmanaged — see the sticky-offset item under P2, which has the same root problem of magic numbers spread across files.

### Secondary: sheet footer overlaps the last filter row

`listings-browser.tsx:162` — the "Show N residences" footer is a `shrink-0 border-t` sibling of the scroll area, which is correct in principle, but the scroll container (L159) has `p-4` with no bottom allowance for the footer's shadowless edge. On the reported device the "Condominium" row sits half-hidden behind the footer with no visual cue that the list continues. Add bottom padding (or `scroll-pb`) to the scroll container so the last row can clear the footer.

## P1 — small-viewport breakage

### Featured residences: autoplay is silently disabled with 3 or fewer listings
`apps/web/src/components/listings/listing-slider.tsx` (used by the homepage via `blocks/featured-residences-slider.tsx`).

Worth correcting a likely assumption: this **is already a Swiper carousel with autoplay** — `modules={[A11y, Autoplay]}` (L74), `AUTOPLAY_MS = 4500` (L16). The reason it can appear not to auto-scroll:

- **L65** `const canLoop = slides.length > 3;` and **L87–95** `autoplay={canLoop ? {...} : false}`. With 3 or fewer featured listings, both `loop` and `autoplay` are off — the rail renders as a static row with dead nav arrows. This is the most likely cause of "it doesn't auto-scroll". Whether that gate is correct depends on how many listings the CMS actually returns for the block; if the intent is always-on motion, autoplay needs to run whenever `slides.length` exceeds `slidesPerView` at the current breakpoint, not a hardcoded `3`.
- **L55–63** the pre-mount fallback is a static `grid gap-5 sm:grid-cols-2 lg:grid-cols-3` of the first 3 cards. Swiper mounts only after `useEffect`, so there is a visible swap from grid to carousel on load, and the first paint shows no motion affordance at all.
- **No `prefers-reduced-motion` guard.** An auto-advancing carousel should stop for users who request reduced motion; there is currently no check. This matters more, not less, if autoplay is made unconditional.
- L70–71 (`onMouseEnter`/`onMouseLeave`) duplicate `pauseOnMouseEnter: true` (L93). Harmless, but redundant — and neither helps touch users, who have no hover to pause with and no pagination dots (`Pagination` module is not loaded) to orient by.

**Fix:** decide the autoplay condition against `slidesPerView` rather than `> 3`, add a `prefers-reduced-motion` guard, add pagination dots for touch, and reduce the mount swap by making the fallback visually match the first carousel frame.

### Floor-plan schematic collapses below ~380px
`apps/web/src/components/listings/property-body.tsx:90` — `grid grid-cols-3 gap-[9px]` with `style={{ gridAutoRows: 'minmax(56px, auto)' }}` and **no breakpoint at all**.

At 320px, after Container padding (`px-[clamp(22px,4vw,64px)]`) and card padding (`p-[clamp(22px,2.6vw,32px)]`), each cell is roughly 68px wide. It holds an `text-[13px] font-bold` room name (L108) with **no truncation and no `break-words`**, plus an `text-[11px]` note (L111). Names like "Owner's Suite" break per character. `great` also spans `col-span-2 row-span-2`, so the schematic is unreadable under ~380px.

**Fix:** `grid-cols-1 sm:grid-cols-2 md:grid-cols-3` ladder, or hide the schematic below `sm` in favour of the text room list.

### Mobile nav menu can be unscrollable in landscape
`apps/web/src/components/site-nav-interactive.tsx:69–89` — the expanded menu renders **inside** a `sticky top-0 z-60` header with **no `max-h` and no `overflow-y-auto`**. In phone landscape (~375px tall), the nav list plus the `size="full"` CTA (L82) exceeds the viewport and the CTA cannot be reached.

**Fix:** `max-h-[calc(100dvh-var(--nav-h))] overflow-y-auto overscroll-contain` on the menu wrapper.

### Map block: fixed height + overlay collision + touch scroll trap
- `apps/web/src/components/listings/property-body.tsx:177` — `h-[340px]` is a hard pixel height and the only non-`clamp()` height on the page. Cramped on desktop, tall on small phones.
- L144 caption overlay: `absolute top-[18px] left-[18px] z-[3] max-w-[62%] …` — at 320px that is ~180px of overlay over a ~276px-wide map, covering most of the pin area.
- `apps/web/src/components/listings/listing-map.tsx` sets `scrollWheelZoom: false` (good) but has **no touch `dragging` / `touchZoom` guard**. A one-finger drag inside a 340px-tall full-width block pans the map instead of scrolling the page — a real scroll trap on mobile.
- L91 `bg-surface-muted size-full` means the parent's fixed height is the only height source; if that height is ever removed the map collapses to 0. No `aspect-ratio` fallback.

### Lead form name row — affects 5 surfaces
`apps/web/src/components/lead-form.tsx:230` — `grid grid-cols-2 gap-3` for First/Last name, no `sm:` variant.

Worst case is the dark card surfaces, all at `p-[clamp(30px,3.4vw,42px)]`: `blocks/lead-capture.tsx:43`, `communities/tour-band.tsx:39`, `listings/concierge-cta.tsx:40`. At 320px: `320 − 44` (Container) `− 60` (card) `− 12` (gap) leaves **~102px per input**. Placeholders and typed values both truncate.

**Fix:** `grid-cols-1 sm:grid-cols-2`.

### Key-facts ribbons clip values at their own breakpoint
- `apps/web/src/components/listings/property-header.tsx:63` — `grid-cols-2 gap-px … sm:grid-cols-3 lg:grid-cols-6`. At exactly `lg` (1024px), six cells share ~960px = 160px each; minus `px-[22px]` (L69) that is ~116px for an `text-[18px] font-extrabold` value such as `$1,250,000` (L74) plus an `uppercase tracking-[0.06em]` label (L77). No `xl:` step, no truncation. The 2-col mobile case at 320px gives ~94px of content.
- `apps/web/src/components/communities/main-content.tsx:78` — same shape (`grid-cols-2 … md:grid-cols-3`, cells at `px-6 py-[22px]`); ~112px of content for values like "1,200–4,800 sq ft".

Also `property-header.tsx:39–44`: price is `text-[clamp(40px,5.2vw,62px)] leading-none` with an inline `ml-3.5 text-[16px]` per-sqft span. At 320px `$1,250,000` at 40px is ~250px wide, the span wraps, and `leading-none` gives the wrapped line no room — the two lines visually collide.

### Community "All N photos" trigger overflows its tile
`apps/web/src/components/communities/gallery-photos-dialog.tsx:17` — `absolute right-4 bottom-4 … px-[17px] py-[11px] text-[14px] font-bold` is ~150–170px wide, but it is rendered as the overlay of the **last small tile** (`communities/gallery.tsx:63`), a ~110px-wide box below md. It overflows its tile and spills across the neighbour. No responsive size or position variant.

Related: `communities/gallery.tsx:14–17` — only the 4-tile case hides overflow tiles below md (L61 `hidden md:block`). The `grid-cols-[1.4fr_1fr]` mosaic itself never collapses to one column, so inside `aspect-[16/10]` at 320px each small tile is roughly 110×95px.

### "The Life" band eats the viewport
`apps/web/src/components/blocks/the-life.tsx:20` — `relative flex min-h-[600px] items-center overflow-hidden text-white`, a hard pixel minimum with no responsive variant. Every sibling band uses `py-[clamp(...)]` instead. On a 360×640 phone this one band nearly fills the screen; in landscape it forces 600px of scroll with the copy centered in dead space.

**Fix:** `min-h-[clamp(420px,70dvh,600px)]` or drop to `py-[clamp(...)]` like its siblings.

### Horizontal scrollers lose padding and give no affordance
- `apps/web/src/components/listings/quick-filter-bar.tsx:41` — `<Container className="flex items-center gap-2.5 overflow-x-auto py-4">`. `Container` supplies `px-[clamp(22px,4vw,64px)]` (`container.tsx:18`), so the scrolling box itself carries the padding. Trailing inline padding collapses at scroll end in most engines: the last pill sits flush against the screen edge and reads as cut off at 360px. No `snap-*`, no fade mask.
- `apps/web/src/components/communities/section-tabs.tsx:57` — `flex … gap-1.5 overflow-x-auto` with `whitespace-nowrap` tabs (L68), inside `Container`. At 320–360px only ~2 of 6 tabs are visible with **no visual hint that more exist**.

**Fix:** move the scroll region inside the padded rail (or add `scroll-px` / a pseudo end-spacer), and add a fade mask or peeking affordance.

### Double horizontal padding
`apps/web/src/components/blocks/communities-strip.tsx:41,49` — `<Container className="grid sm:grid-cols-3">` where each item also carries `px-[clamp(20px,3vw,44px)]`. That is 42px per side at 320px, leaving 236px for a 58px icon plus two lines of copy — a ~160px text column. The item padding assumes it is not nested in the padded rail.

## P2 — consistency and fragility

### Sticky offsets are hard-coded and disagree with each other
The nav's height is content-derived (`site-nav-interactive.tsx:31`, `py-4` + brand mark), but every consumer hard-codes it:

| File | Value |
| --- | --- |
| `communities/section-tabs.tsx:52` | `sticky top-[74px]` |
| `listings/quick-filter-bar.tsx:40` | `sticky top-[73px]` |
| `listings/listings-browser.tsx:134,137` | `scroll-mt-[148px]`, `lg:top-[148px]` |
| `communities/agent-aside.tsx:30` | `lg:sticky lg:top-[150px]` |
| `communities/main-content.tsx:32` | `scroll-mt-[150px]` |
| `listings/property-aside.tsx:42` | `lg:top-24` (96px — inconsistent with the rest) |

Consequences: 73 vs 74 produces a 1px sliver of content scrolling between the two bars; anchor jumps land under the sticky bars whenever real bar height ≠ the literal. Two stacked sticky bars also consume ~150px of a 640px-tall viewport before any content renders.

**Fix:** one CSS custom property (e.g. `--nav-h`, `--subnav-h`) set once and referenced everywhere.

### Unsafe grid track on the PDP
`apps/web/src/app/listings/[slug]/page.tsx:116` — `lg:grid-cols-[1fr_384px]`. `1fr` (not `minmax(0,1fr)`) lets the left column's min-content push the grid past the viewport around 1024–1100px. Only `PropertyBody`'s root `min-w-0` (`property-body.tsx:189`) prevents it today. The community page gets this right: `app/communities/[slug]/page.tsx:85` uses `lg:grid-cols-[minmax(0,1fr)_372px]`.

### Sticky PDP aside has no height guard
`apps/web/src/components/listings/property-aside.tsx:42` — `lg:sticky lg:top-24` with no `max-h` / `overflow-y-auto`. A tall broker card plus tour form can exceed viewport height on a short laptop, making the bottom unreachable. The listings aside already guards this correctly: `listings-browser.tsx` uses `lg:max-h-[calc(100dvh-160px)] lg:overflow-y-auto`.

### PDP mosaic is not dynamic — it always reserves space for 5 photos
`apps/web/src/components/listings/property-gallery.tsx:36` — the grid template is hardcoded regardless of how many photos the listing actually has:

```
md:grid-cols-[1.6fr_1fr_1fr] md:grid-rows-2
```

That is a 3×2 = 6-cell mosaic with the hero spanning `md:row-span-2` (L38), i.e. **exactly 5 photos**. A listing or community with 2 images renders the hero plus one tile and leaves **3 empty grid cells** — the layout still looks like a 5-photo mosaic with holes in it. This is the reported behavior.

`communities/gallery.tsx:12–26` already solved this properly with tile-count-keyed template maps (`GRID_BY_TILES` / `LEAD_BY_TILES`) and complete literal class strings so Tailwind's CSS-first scanner can see them. The PDP simply never adopted the pattern.

**Fix — mirror the communities approach.** Derive `tileCount` from the images that follow the hero and key both the grid template and the hero's row span off it, so every cell is filled at every count:

| Tiles after hero | Total photos | Grid template | Hero span |
| --- | --- | --- | --- |
| 0 | 1 | `md:grid-cols-1 md:grid-rows-1` | — |
| 1 | 2 | `md:grid-cols-2 md:grid-rows-1` | — |
| 2 | 3 | `md:grid-cols-[1.6fr_1fr] md:grid-rows-2` | `md:row-span-2` |
| 3 | 4 | `md:grid-cols-[1.6fr_1fr] md:grid-rows-3` | `md:row-span-3` |
| 4 | 5+ | `md:grid-cols-[1.6fr_1fr_1fr] md:grid-rows-2` | `md:row-span-2` |

Each row fills its columns exactly, so there are no gaps at any count. Two additional details worth handling in the same pass:

- **`sizes` must vary with the template.** L58's `sizes="(max-width: 768px) 100vw, 50vw"` and L78's `sizes="25vw"` are written for the 5-photo case. In the 2-photo layout the hero is ~46vw and the single tile is also ~46vw, so the tile under-fetches badly at `25vw`. Key the `sizes` strings off `tileCount` too.
- **Keep the literals complete.** Do not build these class strings by interpolation (`md:grid-cols-[${x}]`) — Tailwind's scanner will not see them and the styles will be missing in production. This is exactly why `communities/gallery.tsx:10–11` carries that comment.

Also on L36: `md:h-[clamp(420px,42vw,560px)]` — on a 1280×720 laptop, 42vw ≈ 537px of a 720px viewport is consumed by the mosaic alone. And the mobile hero is `aspect-[16/10]` while the desktop mosaic is closer to `1.92/1`, so the crop framing shifts across the md boundary. The communities gallery avoids this by setting `aspect-[16/10] md:aspect-[1.92/1]` on the grid itself (`communities/gallery.tsx:47`) rather than a clamped pixel height — worth adopting at the same time.

### Missing `min-w-0` / truncation
- `property-body.tsx:48` spec key/value rows — `flex items-start justify-between gap-[18px]` with neither child having `min-w-0`. A long unbroken MLS value cannot shrink and overflows its cell.
- `listings/listing-card.tsx:85` — `{communityName} · {city}` with no `min-w-0` or `truncate`. Long community names wrap to 2–3 lines and desynchronize card heights in the `sm:grid-cols-2 lg:grid-cols-3` grids.
- `listings/listing-card.tsx:88–92` stats row — `flex-1` and `border-l pl-[13px]` with no `min-w-0`; borderline for a 5-digit sqft in the 2-col mobile grid.

### Layout-shift and misc

At 320px both fields shrink well below their basis; the placeholder "Community, city, or residence name" truncates to a few words. `min-w-0` means it degrades rather than overflows, but there is no small-screen stacking or label treatment.
- `listings/listings-browser.tsx:195` — `relative min-w-[200px]` on the Sort select, inside a `flex items-center gap-3` with a `whitespace-nowrap` label (L191). Combined min width ~245px against ~276px available at 320px; any label growth or localization forces overflow.
- `communities/main-content.tsx:173` — `font-serif text-[64px] leading-none` with no `clamp()`. The only oversized display size in the app lacking one; fits today only because it is centered in a single mobile column.
- `blocks/meet-the-owner.tsx:17,21,32` — decorative absolute layers (`-bottom-[22px] -right-[22px]`, `-left-4 top-[26px]`) and a badge at `absolute -left-[18px] bottom-[30px]` deliberately break the rail at all widths. Only `body { overflow-x-clip }` prevents a mobile scrollbar; at 320px the badge's left edge is clipped rather than visible.
- `blocks/testimonials.tsx:141` — `absolute -left-1 -top-[0.28em] text-[clamp(120px,13vw,190px)]`. The 120px floor applies at mobile where 13vw would be ~42px; the glyph overhangs the container padding and is clipped by the section's `overflow-hidden` (L80).
- `site-footer.tsx:9` — re-implements the rail (`mx-auto max-w-[1440px] px-[clamp(22px,4vw,64px)]`) instead of using `Container`. Two copies of the padding assumption to keep in sync.
- `property-gallery.tsx:39` — badge stack `absolute top-4 left-4 z-[3] flex flex-wrap gap-[9px]` has no max-width. The two `uppercase tracking-[0.1em]` pills at `px-[13px] py-[7px]` need ~230px; at 320px with a long `statusLabel` they wrap to two rows over the image and can cover much of the hero.
- `property-gallery.tsx:58` — `sizes="(max-width: 768px) 100vw, 50vw"` over-fetches slightly; the hero is ~1.6/3.6 of a 1440px rail ≈ 600px. L78's unconditional `sizes="25vw"` is harmless only because those tiles never render on mobile.

## Addendum — "Similar Homes" promised a place it did not deliver (fixed)

Reported after the original audit, with a screenshot showing the heading "More residences in **Fort Myers Beach**" above two Bonita Springs cards.

Root cause was `app/listings/[slug]/page.tsx`:

```js
.filter((l) => l.community === detail.community || l.type === detail.type)
```

The `||` meant "same community **or** same property type", so a Bonita Springs condo qualified for a Fort Myers Beach listing purely by being a condo — while the heading unconditionally printed `communityName`. Because `active` is not ordered by location, whichever type-matches came first won the three slots.

Replaced with a location-first tiered fill: same community → same city → same property type elsewhere. The heading is now only allowed to name a place when **every** card actually shares it (`scopeLabel`), otherwise it falls back to "Residences you may also like." A local `toTitleCase` handles MLS cities, which arrive upper-cased (`FORT MYERS BEACH`).

Worth knowing for future data changes: `ListingCard.community` is the **area** slug (`normalize.ts:261` maps `area.slug`/`area.name`), and areas are finer-grained than cities — `Bonita Bay` and `Valencia Bonita` are both in Bonita Springs. All five current areas hold ≥16 active listings, so tier 1 always fills three slots and **tiers 2 and 3 are currently unreachable**; they only matter if an area with fewer than three listings is added.

Verified: `/listings/1801-estero-blvd-…` → "More residences in Fort Myers Beach." with all three cards Fort Myers Beach; `/listings/12445-dahlia-ct-…` → "More residences in Valencia Trails." with all three in Valencia Trails.
